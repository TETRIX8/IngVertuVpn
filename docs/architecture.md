# Архитектура

Дата снимка: 2026-11-15. Это operational map, не полноценная схема сетевой маршрутизации.

## Компоненты

1. Telegram bot `@IngVertuVpn_bot` работает на основном хосте. Он управляет Telegram-учётками и вызывает Remnawave API для синхронизации подписчиков.
2. Remnawave Panel, PostgreSQL и Redis запущены контейнерами Docker на том же основном хосте. Панельный веб-интерфейс — `https://panel.vertuwpn.ru`.
3. Публичный subscription hostname `https://sub.vertuwpn.ru`; маршрут `/api/sub/<short-id>` проксируется к Remnawave. Ответ для проверенного пользователя — base64-кодированный список из двух `ss://` ссылок.
4. Два подключённых Remnawave Node размещены отдельно. Подписка включает `91.205.220.23:1234` и `195.96.132.187:1234`. Management API Node работает на отдельном закрытом порту; правила ограничивают управление со стороны Panel.
5. Cloudflare обслуживает DNS зоны `vertuwpn.ru`. Дополнительный CDN/proxy режим не является необходимым условием для выдачи subscription payload.

## Поток выдачи

Бот записывает пользователя в SQLite и синхронизирует пользователя/срок/лимиты с Remnawave через scoped API token. Remnawave выдаёт публичный subscription payload по короткому ID. Оплата пока заглушена; не включать реальные provider checkout без отдельной реализации и утверждения.

## Что проверено

- На 2026-11-15 бот и Remnawave containers были active/healthy.
- Синтетический и действительный тест подписки отвечали HTTP 200; фактический payload содержал два `ss://` endpoint-а для первых двух узлов.
- Старый код формировал неподдерживаемый `/conf/<uuid>`. Исправлено: новые ссылки ведут на рабочий `/api/sub/<short-id>`, а legacy `/conf` перенаправляет туда.
- Узел `194.5.65.28` не подключён: предоставленный SSH пароль был отвергнут при проверке. На него нельзя ссылаться как на настроенный/действующий.

Не делайте вывод о подключении клиентского приложения только по HTTP 200 subscription: fetch подписки и TCP/handshake туннеля — разные проверки.
